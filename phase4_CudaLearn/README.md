# CudaLearn — Phase 4: CUDA

ロードマップ Phase 4 の学習記録。「CPU 版 → CUDA 版 → ベンチマーク」を作り、
**GPU の計算は速いが、転送コストで負けることがある**という感覚を数値で確認する。

## 環境(2026/11/02 に再測定)

- GPU: NVIDIA GeForce RTX 3060 Laptop (6GB)、WSL2 (Ubuntu)、ドライバ 596.36
- CUDA: nvcc 12.0
- ビルド: `nvcc -O2 -arch=native <file>.cu -o <name>`(ホスト側も最適化あり)
- 計測: 各条件を **3 回**実行し、表は**中央値**(カッコ内が 3 回の範囲)
- 生の出力: [results.txt](results.txt)

## 作ったもの

| ファイル | 内容 |
|---|---|
| `vecadd.cu` | ベクトル加算の最小 CUDA カーネル |
| `vecadd_bench.cu` | ベクトル加算を CPU と GPU で比較。GPU は H2D 転送・カーネル・D2H 転送を分けて計測 |
| `vecheavy_bench.cu` | 1 要素あたりの演算量 `K` を変えて、演算強度と GPU の優位の関係を見る(`-DK=…`) |
| `vecheavy_stable.cu` | 上の式を誤差が増えない形(係数 0.5)に直した版。CPU と GPU の結果が一致する |
| `diag_precision.cu` | `vecheavy_bench` の検証失敗の原因調査用(CPU float / GPU float / CPU double の誤差比較) |
| `matmul_bench.cu` | 行列積 C = A×B の CPU(3 重ループ)と GPU(2 次元スレッド配置)の比較 |
| `matmul_tiled.cu` | shared memory でタイル化した行列積。naive 版との比較(`-DN_SIZE=…`) |
| `matmul_analysis.cu` | naive / タイル 16・32 / レジスタタイル / cuBLAS を同じ条件で比較し、理論ピークの何 % かを出す(表 5) |

## 測定結果

### 1. ベクトル加算(n = 1677 万要素、67MB × 3)

| | 時間 |
|---|---|
| CPU | 25.1 ms (23.1–26.5) |
| GPU カーネルのみ | 3.1 ms (2.3–3.1) |
| GPU 転送(H2D + D2H) | 29.7 ms (28.9–31.0) |
| **GPU 合計(転送込み)** | **32.8 ms** (31.3–34.1) |

カーネル自体は CPU の約 8 倍速いが、転送が約 30 ms かかるため**合計では CPU より遅い**。
計算が 1 要素あたり足し算 1 回しかない(演算強度が低い)ので、GPU の速さが転送で消える。

### 2. 演算強度を上げる(同じデータ量、1 要素あたり K 回の sin/cos)

式を直した `vecheavy_stable.cu`(`x = sinf(x)*0.5f + cosf(y)`)で測定。**K=1〜200 の全てで CPU と GPU の結果が一致(errors=0)**。

| K | CPU | GPU カーネル | GPU 転送 | GPU 合計 | 速度比(カーネルのみ) | 速度比(転送込み) |
|---|---|---|---|---|---|---|
| 1 | 152.8 ms | 3.5 ms | 53.7 ms | 58.3 ms | ×39.3 (33.9–45.9) | ×2.6 (1.7–2.6) |
| 5 | 641.2 ms | 3.7 ms | 83.1 ms | 87.3 ms | ×172.7 (127.1–181.7) | ×7.3 (7.0–11.3) |
| 20 | 3.94 s | 6.7 ms | 75.9 ms | 82.0 ms | ×590 (584–678) | ×49.3 (33.2–50.7) |
| 200 | 44.8 s | 33.7 ms | 74.2 ms | 107.9 ms | ×1342 (1331–1372) | ×416 (408–450) |

転送時間はデータ量が同じなのでほぼ変わらない(約 54〜83 ms。D2H のばらつきが大きく、3 回のうち 1 回だけ 2 倍近く遅いことがある)。
K=1 はカーネルが 39 倍速くても、転送込みでは 2.6 倍しか出ない。K を増やすと転送の割合が下がり、K=200 では転送込みでも約 400 倍になる。
元の式(`vecheavy_bench.cu`、`sinf(x)*y + cosf(y)`)でも時間の傾向は同じだった(K=200 で転送込み ×530)が、結果の検証は通らない(下の「注意」参照)。

### 3. 行列積 512×512(naive、1 スレッドが出力 1 要素を担当)

| | 時間 |
|---|---|
| CPU | 122.1 ms (117.7–134.7) |
| GPU カーネル | 1.49 ms (1.35–1.71) |
| 速度比 | ×81.9 (78.8–87.0) |

演算量 O(N³) に対してデータ量は O(N²) なので、ベクトル加算と違って GPU が転送なしで大きく勝つ(ここでは転送時間は含めていない)。

### 4. タイル化(shared memory)の効果

| N | CPU | GPU naive | GPU tiled | naive → tiled |
|---|---|---|---|---|
| 512 | 136.9 ms | 0.43 ms | 0.37 ms | ×1.17 (1.00–1.21) |
| 1024 | 3.03 s | 3.09 ms | 2.48 ms | ×1.33 (0.85–1.53) |
| 2048 | 38.3 s | 23.8 ms | 20.0 ms | ×1.22 (1.19–1.24) |

タイル化の効果は**約 1.2 倍**で、期待したほど大きくはなかった。N=1024 は測るたびの揺れが大きく(0.85–1.53)、
この条件だけでは「タイル化が速い」と言い切れない。N=2048 は 3 回とも ×1.2 前後でそろっている。

### 5. なぜタイル化は 1.2〜1.4 倍にとどまるのか(2026/11/04 追加調査)

[matmul_analysis.cu](matmul_analysis.cu) で、同じ行列積を 5 通りの実装で比べた(生の出力: [results_matmul_analysis.txt](results_matmul_analysis.txt))。
`regtile` は、1 スレッドが 4×4=16 個の出力を持ち、共有メモリから読んだ値をレジスタ上で使い回す版(ブロック 64×64、K 方向 16)。
cuBLAS(`cublasSgemm`、Tensor Core を使わない FP32 設定)を、到達できる上限の目安にした。N ごとに 3 回測った最小時間から、中央値を載せる。

| N | naive | tiled16 | tiled32 | regtile | cuBLAS |
|---|---|---|---|---|---|
| 1024 | 914 GFLOPS | 1110 (×1.22) | 1079 (×1.18) | 4630 (×5.1) | 7085 (×7.8) |
| 2048 | 782 GFLOPS | 1068 (×1.37) | 1026 (×1.31) | 5256 (×6.7) | 7524 (×9.6) |
| 4096 | 764 GFLOPS | 1044 (×1.37) | 1016 (×1.33) | 4704 (×6.2) | 6732 (×8.9) |

この GPU の FP32 理論ピーク(30 SM × 128 FMA/clk × 2 FLOP × 1.70 GHz)は約 13.1 TFLOPS。その何 % かで見ると:
naive 約 6%、tiled16 約 8%、regtile 約 36〜40%、cuBLAS 約 52〜57%。結果は全実装で cuBLAS と一致した(最大相対誤差 N=4096 で 7e-6)。

**測定から言えること**

1. **タイル化(tiled16)は、理論ピークの 8% しか出ていない。** 「データを再利用して遅いグローバルメモリの読みを減らす」という目的は果たしているはずなのに、
   速くならない。したがってボトルネックは、グローバルメモリの帯域ではない。
2. **タイルを 16→32 に大きくしても速くならない(むしろ少し遅い)。** グローバルメモリの読みが半分になっても効かないので、これもグローバルメモリが律速ではないことと合う。
3. **同じ共有メモリを使っても、レジスタ側で再利用すると 4〜5 倍に伸びる(tiled16 → regtile)。** tiled16 は FMA 1 回につき共有メモリを 2 回読む(A と B 各 1 回)。
   regtile は 4×4 を持つので、FMA 16 回に対して共有メモリ読みは 8 回(= FMA 1 回あたり 0.5 回)。伸びた分は、
   「共有メモリの読み出し命令の数・帯域」が tiled16 の上限になっていたことと合う。
4. **naive が最初から 6% 出ているのも、キャッシュの効果と読める。** naive の同じ warp(32 スレッド)は、B を連続したアドレスで読み(1 回のメモリ要求にまとまる)、
   A は全員が同じアドレスを読む(1 回の要求で全員に配られる)。それを L1/L2 キャッシュが吸収するので、「再利用がなくて遅い」状態にはならない。

以上から、「共有メモリ版が naive より 1.2〜1.4 倍しか速くない」のは、**この GPU では naive のグローバルメモリ読みが大きな問題になっておらず、
tiled16 は代わりに共有メモリの読み出し(FMA 1 回あたり 2 回)が上限になるため**、と考える。タイル化そのものが悪いのではなく、
共有メモリだけでは足りず、レジスタでの再利用(regtile)まで進めて初めて大きく伸びる。

**確認できていないこと(正直な注意)**
- 上の 1〜4 は**時間の比較からの推論**で、プロファイラの数値で直接確かめてはいない。Nsight Compute は、この PC で GPU のカウンターが一般ユーザーに許可されておらず
  (`ERR_NVGPUCTRPERM`)、実行できなかった。許可するには、Windows 側の NVIDIA コントロールパネル →「デスクトップ」→「開発者」→
  「GPU パフォーマンス カウンターへのアクセスを全てのユーザーに許可」を有効にして再起動する(PC の設定変更なので、自分では変更していない)。
  有効にしたら、`ncu --section MemoryWorkloadAnalysis --section ComputeWorkloadAnalysis ./matmul_analysis 2048` などで、共有メモリのパイプの使用率を確かめられる。
- ノート PC の GPU なので、クロックは温度や電力で変わる。理論ピークに対する % は最大クロック 1.70 GHz を基準にした目安。
- WSL では、Linux 版の `libcuda.so`(`/lib/x86_64-linux-gnu`)が WSL 用のもの(`/usr/lib/wsl/lib`)より先に読まれ、`cublas` を使うプログラムだけ
  「no CUDA-capable device」で失敗した。`LD_LIBRARY_PATH=/usr/lib/wsl/lib` を付けると動く(測定はこの設定で実行)。

## 学んだこと

- GPU の評価は「カーネルが何倍速いか」だけでなく**転送込みの合計**で見る。演算強度が低いと転送で負ける。
- 同じ GPU でも、演算強度(K や行列サイズ)で優位が ×2 にも ×500 にもなる。
- 時間は `steady_clock` の前後に `cudaDeviceSynchronize()` を挟んで測っている。非同期実行なので同期しないと値が意味を持たない。

## 注意・未解決

- **`vecheavy_bench` (K≥5) の検証が失敗する**: `errors` が約 1500 万(全 1677 万要素のうち約 9 割)になる。K=1 では 0 件。K=5 → 1205 万、K=20 → 1613 万、K=50 → 1591 万。
  **原因を調べた結果: GPU のバグではなく、計算式が誤差を増幅する式だった。** `x = sinf(x) * y + cosf(y)` を繰り返すと、1 回ごとに誤差がおよそ `y` 倍(`y` は 1〜最大約 170)に広がる。
  float の丸め誤差(約 1e-7)は K 回後に `y^K` 倍へ増える。そのため、どんな float の実装でも K が大きいと結果が一致しなくなる。
  [diag_precision.cu](diag_precision.cu) で、同じ式を CPU float・GPU float・CPU double の 3 通りで計算して確かめた(n=2^20、`y` は 1〜11.5):
  - CPU float も GPU float も、double(基準)からの誤差はほぼ同じ。K=5 で 18〜19% の要素が 1e-4 を超え、K=10 で約 56% に増え、K≥10 では最大誤差が 23 に達する(値の振幅と同程度で、結果がほぼ無意味になる)。
  - つまり GPU だけが間違っているのではなく、CPU の float も同様に間違っている。
  - K=1〜2 では誤差が 1e-5 以下で、検証は通る。
  - `y` が大きい要素ほど CPU と GPU の差が大きい(K=5 で、`y`≈1〜2 では差 0、`y`≈10 では約 2.5e-5)。
  対応: 係数を 0.5 にした `vecheavy_stable.cu` で K=1・5・20・200 を 3 回ずつ測り直し、**全て errors=0** になった(上の表 2)。`vecheavy_bench.cu` は、過程の記録として元の式のまま残している。
- `vecadd_bench` と `matmul_bench` にはウォームアップがなく、1 回だけの計測。`matmul_tiled` には 1 回の空打ちがある。
- タイル化の効果が小さい理由は、時間の比較で調べた(表 5)。ただしプロファイラ(Nsight Compute)での直接の確認は、GPU カウンターの権限がなく未実施。
- 元の学習時(10 月)の測定値は残っておらず、上の数値は 2026/11/02 に再測定したもの。

## 再現手順

```bash
nvcc -O2 -arch=native vecadd_bench.cu -o vecadd_bench && ./vecadd_bench
nvcc -O2 -arch=native -DK=1   vecheavy_bench.cu -o vecheavy_k1   && ./vecheavy_k1
nvcc -O2 -arch=native -DK=200 vecheavy_bench.cu -o vecheavy_k200 && ./vecheavy_k200   # CPU 側が約 1 分かかる
nvcc -O2 -arch=native matmul_bench.cu -o matmul_bench && ./matmul_bench
nvcc -O2 -arch=native -DN_SIZE=1024 matmul_tiled.cu -o mt1024 && ./mt1024              # N は 16 の倍数
nvcc -O3 -arch=native matmul_analysis.cu -o matmul_analysis -lcublas
LD_LIBRARY_PATH=/usr/lib/wsl/lib ./matmul_analysis 2048                                # N は 64 の倍数(WSL のみ LD_LIBRARY_PATH が必要)
```
