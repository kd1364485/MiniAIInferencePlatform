# TcpServer

Phase 2 作品：High Performance TCP Server

echo server から始めて、
single thread → multi thread → thread pool → non-blocking I/O (epoll)
まで育てる。

(Phase 6 で ONNX Runtime 推論サーバー `infer_server` に発展した。再現手順は次の節。)

## ビルドと実行（再現手順）

必要なもの: g++ (C++20)、cmake 3.16+、ONNX Runtime の C++ 用 CPU 版パッケージ、
Python + torch + onnx（モデル作成用）、MNIST の IDX ファイル（正解率の確認用。重いモデルの測定だけなら不要）。

```bash
# 1. ONNX Runtime(C++ 配布パッケージ)を展開し、場所を -DORT_DIR で渡す
#    (既定は ../OnnxLearn/ort。無いと分かりやすいエラーで止まる)
cmake -S . -B build -DORT_DIR=/path/to/onnxruntime-linux-x64-x.y.z
cmake --build build -j

# 2. 重いモデルを作る (784→2048→2048→10, 約5.8M param, バッチ軸可変)。models/ は git 管理外
python tools/export_mlp.py models/mlp_dyn.onnx

# 3. サーバー起動:  infer_server <model.onnx> [workers=8] [intra_op=1] [per_worker_session=0] [max_batch=1] [infer_threads=0]
#    infer_threads=0: インライン(I/O worker が自分で Run())。1以上: 共有 Request Queue 経由の推論専用 worker
./build/infer_server models/mlp_dyn.onnx 2 1 0 8 6      # I/O 2本 + 推論 6本 + batch 8

# 4. ベンチ:  infer_bench <接続数> <秒> [MNISTのディレクトリ | dummy]   (dummy = 乱数画像。重いモデル用)
./build/infer_bench 100 5 dummy
```
サーバーは SIGTERM で止めると、`Run()` の平均・平均バッチ・(キュー版は)キュー待ち時間を表示する。
`mnist.onnx` はバッチ軸が可変（`(batch,1,28,28)`）なので `max_batch>=2` でも動く。

GPU 版（Phase 7）: ONNX Runtime の GPU 版 C++ パッケージ（例: `onnxruntime-linux-x64-gpu_cuda13-1.30.0.tgz`）を展開し、
`-DORT_DIR=…/ort_gpu` でビルドする（同じビルドで cpu / cuda / trt のどれも選べる）。CUDA 13・cuDNN・TensorRT 10 の
pip パッケージ（`nvidia-*`、`tensorrt-cu13`）が入った Python を `PYTHON=` に指定し、`tools/run_gpu_env.sh` 経由で起動する:
```bash
PYTHON=/path/to/venv/bin/python tools/run_gpu_env.sh ./build/infer_server models/mlp_dyn.onnx 2 1 0 128 1 trt-fp16
#                                                      モデル                I/O 内部 専用 batch 推論 provider(cpu|cuda|trt|trt-fp16)
PYTHON=... python tools/server_bench.py ./build/infer_server ./build/infer_bench models/mlp_dyn.onnx   # 条件を総当たりで測る
```
GPU プロバイダの失敗（ライブラリが無い等）は起動時に例外で止まる（黙って CPU に落ちない）。

この実験から見えること
1. スループットは「カバー率」で決まる

4→32本はほぼ線形に伸びています。理由は「捌ける接続数が増えたから」であって、1接続あたりの速度が上がったわけではありません。max=5000ms がずっと残っているのが証拠＝キューに飢餓接続がいた。

M3(pool=100) ≈ M2(thread-per-conn) ≈ 67k vs 63k

「接続数と同じ数のスレッドをプールしておく」は、事実上「接続ごとにスレッドを作る」と同じモデルです。M3はワーカー数が足りないM2だったわけです。

3. p50はむしろ悪化する（273→1069μs）

ワーカーが増えると同時に動くスレッドも増え、スケジューラが切り替える回数が増える → 1リクエストあたりの待ちはむしろ伸びる。「数を増やすと速くなる」は並列度が足りない領域までで、その先はオーバーヘッドとトレードオフ。

4. そして M4（72k・スレッド1本）が依然最速

同じ「全接続を捌く」結果を、M4はスレッド1本・スタック数MBで達成しています。「同じことを、少ない資源でやる」——これがepollの価値であり、スケーラビリティという言葉の本質です

### 学んだこと

- eventfd = epoll_waitで寝てるスレッドを起こす通知専用fd(writeで+1/readで0リセット)
- epollはスレッドごとに専用にするとロック不要（sharding）
- スレッド間の受け渡しは「共有キュー+mutex」＋「起こす手段(eventfd)」の2セット
- data.fdは登録時に預けた目印がそのまま返る（どのfdが起きたかの判別）
- 結果: M7 67k(100c)/80k(200c) vs M4 72k/87k。スループットはM4、尻尾(max)はM7が4倍安定
- 「軽い処理では受け渡しコストが負ける。shardingはCPU重い処理向き」


【起動時】
mainがlisten_fdと8人のworker(専用epoll+eventfd)を作る
worker達はepoll_waitで即寝る

【接続時】(フェーズ1)
client connect → listen_fd読める → acceptor起きる
→ acceptでcfd取得 → worker選択 → pendingにpush → eventfd write

【受け取り】(フェーズ2)
workerのepollがevent_fdで起きる → read(efd)でベル消費
→ pendingからcfd取出し → 自分のepollにEPOLLIN登録

【通信時】(フェーズ3)
clientがsend → cfdが読める → 担当workerのepoll_waitが起きる
→ recv → send(エコー) → 寝る

【切断時】
clientがclose → cfd読める → recvが0返す → epoll_ctl(DEL)+close → 寝る

M4(epoll×1):
  100conn: 72,484 req/s  max=210ms
  200conn: 87,115 req/s  max=416ms
→ スループットはM4が上、でも尻尾(max)はM7が4倍安定
→ 「shardingはCPU重い処理向き。軽い処理では受け渡しコストが負ける」

Q1. epollの「寝る」と「起きる」 epoll_wait でスレッドは「寝る」と言いましたが、カーネルとスレッドの間で実際に何が起きているか説明してください。CPUを食わずに待てるのはなぜでしょう？

epoll_waitすると:
  1. スレッドはカーネルに「このfdセットを見張ってて」と委託
  2. カーネルがスレッドを「実行可能リスト」から外して待ち行列へ移す
     → CPUが振り分けられない = 0%消費
  3. 監視中のfdが「読める」になったら、カーネルが
     スレッドを実行可能リストに戻す

     自分で確認しに行くのではなく、カーネルが代わりに見張り＆起こす。だからbusy-loop（while(1){チェック}）と違ってCPUを食わない。


Q2. mutex と atomic の違い M3のキューは mutex で守り、benchのカウンタは atomic にしました。この使い分けはなぜでしょう？atomicで全部統一しない理由は？

守れる範囲	仕組み
mutex	複数行・複数操作の「まとまり」	ロックを取れるのは1スレッドだけ（他は待つ）
atomic	1命令だけ（+1、読み、書きなど）	CPUが不可分に実行、待ちなし
queue.push は内部で「メモリ確保→ポインタ繋ぎ→サイズ更新」等の複数操作なのでatomicでは守れない→mutexが要る。++カウンタ は1命令なのでatomicで十分。「守りたい単位」で選ぶのが答えです。


Q3. eventfdはなぜ必要だったか M7で「キューにpushするだけ」ではなく write(eventfd) も必要だった理由を説明してください。

write(eventfd) → 「起きろ」の合図を送る側（acceptor）
read(eventfd)  → 合図を消費する側（worker）
なぜ必要か：キューにpushしても、寝てるworkerには届かない。workerはepoll_waitの中で待っているので、「箱に入れた」だけでは気づかない。event_fdに書くと「event_fdが読める」=EPOLLINが発生し、epoll_waitが起きる。キュー=仕事の中身、eventfd=起こす手段、別々に必要。


Q4. M7がM4に（スループットで）負けた理由 8スレッドのM7が1スレッドのM4に負けたのはなぜか。逆にM7のmaxが4倍改善した理由も。

負けた理由：受け渡しコスト（mutex+eventfd+キュー処理）が1往復の仕事（echo = ただのコピー）より重かった。正解です。

max改善の理由は「1スレッドの仕事量削減」ではなく：「1ワーカーが遅延しても残り7ワーカーは動く」分離効果です。M4は1本のループが詰まると200接続全部が止まるが、M7はワーカー単位でしか詰まらない→最悪待ちが減る。


Q5. data.fd の目印 epollは「どのfdが起きたか」をどうやって教えてくれるか。events[i].data.fd に9が入っている仕組みを説明してください。

「epollがfd番号を自動で教えてくれる」のではなく、登録時に自分で目印を仕込んでいるのがポイント：



cpp
epoll_event ev{};
ev.data.fd = 9;          // ← ここで「9という目印」をカーネルに預ける
epoll_ctl(ep, ADD, 9, &ev);
 
// 後日fd9が読める → カーネルが「あなたが預けた目印」を events[i].data.fd に書き戻す
// events[i].data.fd == 9 が返る
「カーネルがfd9と判断して9を返す」のでなく「あなたが預けた9をそのまま返す」という対応表です。

3b. __syncthreads() — 待ち合わせ


cpp
__syncthreads();
**「ブロック内の全スレッドがここに来るまで待つ」**バリアです。

なぜ必要か：スレッド0が As[5][3] を読もうとしたとき、その値はスレッド(5,3)が書いたものです。スレッド(5,3)がまだ書き込みを終えていなければゴミを読んでしまう。だから**「全員の書き込みが終わるまで待つ」**ために全員で止まり合います。


「遅いメモリは少ない回数で、速いメモリで何度も使い回す」がGPU最適化の鉄則




Q1. CPUとGPUの構造の違い / 演算強度


CPU: 少数精鋭(8-24コア)。複雑な制御・分岐・連続処理が得意
GPU: 大勢力(数千コア)。単純計算の大量並列が得意
 
「GPUは速い」の真偽は演算強度(=1バイトあたりの計算量)で決まる:
- 演算強度が高い(matmul, 重い計算) → GPU圧勝 (転送コストを回収できる)
- 演算強度が低い(vec_add, 軽い作業) → 転送コストが支配的でCPU同等以下
 
M3で実測: vec_addはGPU kernelだけなら4倍速いが、転送込みだと負ける
M4で実測: K=200(重い計算)にしたらGPUがx130圧勝
Q2. <<<>>> とスレッド割り当て


vec_add<<<4096, 256>>>:
  4096 = ブロック数
  256  = 1ブロックあたりのスレッド数
  → 合計 4096×256 = 1,048,576 スレッドが起動
 
i = blockIdx.x * blockDim.x + threadIdx.x:
  blockIdx.x = 自分が何番目のブロックか (0〜4095)
  blockDim.x = 1ブロックのスレッド数 (=256)
  threadIdx.x = ブロック内での自分の番号 (0〜255)
  → 全体で通算何番目の要素を担当するかを計算
  例: blockIdx=2, threadIdx=5 → i = 2*256+5 = 517番目の要素を計算
Q3. メモリの2つの世界


h_a = host(CPU)のメモリ。d_a = device(GPU)のメモリ。
両者は物理的に別世界(別のメモリ空間)。ポインタを直接混用できない
  - CPUコードから d_a[i] を触るとクラッシュ
  - GPUカーネルから h_a[i] も触れない
 
cudaMemcpy(..., cudaMemcpyHostToDevice):
  「CPUの配列をGPUのメモリへコピー」する転送API
  GPUが計算するにはデータがGPUの手元(VRAM)にある必要があるため
 
対応: cudaMalloc(GPUで確保) ⇔ cudaFree(GPUで解放)
      new[]      (CPUで確保) ⇔ delete[](CPUで解放)
Q4. __shared__ と __syncthreads()


__shared__:
  ブロック内の全スレッドが共有できるオンチップメモリ。
  global memoryより約10倍速い。「手動キャッシュ」で
  何を置くかはプログラマが決める(CPUキャッシュの自動と違う)
 
__syncthreads() を2回入れた理由:
  1回目(読み込み後): 「全スレッドが shared への書き込みを終えた」ことを確認
                     → まだ書き終わっていない値を読むのを防ぐ
  2回目(計算後):     「全スレッドが shared の読み出しを終えた」ことを確認
                     → まだ読んでいる値を次のタイルで上書きするのを防ぐ
  両方ないと「読み中に上書き」or「書き中に読み」の競合が起きる
Q5. data.fd との比較 / スレッド番号の知り方


epoll:
  登録時に自分で data.fd に「目印」を預ける → 起きたとき返される
  (開発者が値を決める)
 
CUDA:
  <<<4096,256>>> で起動した瞬間、GPUが各スレッドに座標を自動で割り当てる
    blockIdx.x = 自分のブロック番号
    threadIdx.x = ブロック内での自分の番号
    blockDim.x = ブロックのサイズ
  カーネル内でこれらを読んで担当要素を逆算する
  (GPUが値を決める。預けるのではなく「自分の座標が最初から見える」)

## 2026/10/14　M2（Run() が伸びる原因の切り分け）==================================

### やったこと
M1 で「worker を増やすと ORT Run() の平均が伸びる」ことが分かった。原因を1つずつ潰した。
- `taskset` で bench とサーバーのコアを分離

### 結果 (mnist.onnx, intra_op=1)
サーバー内 (100接続, 5秒, Run()平均):
| 条件 | Run() 平均 | req/s |
|---|---|---|
| workers=1 | 25〜28 us | 28〜32k |
| workers=4 (HT共有 / 物理コア1本ずつ) | 67 / 66 us | 約47k |
| workers=8 Session共有 | 113〜120 us | 50〜53k |
| workers=8 Session専用 | 102〜108 us | 53〜56k |

ネットワークなし (run_bench, Run()だけ):
| N | 1プロセスN スレッド 共有 | 1プロセスN スレッド 専用 | Nプロセス x1 |
|---|---|---|---|
| 1 | 15 us | 15 us | 16 us |
| 4 | 21 us | 21 us | 20 us |
| 8 | 41〜45 us | 31〜32 us | 31 us |

### 分かったこと
- 否定: bench とのコア奪い合い（taskset で分離しても 118→121us で変わらず）
- 否定: ハイパースレッディング（同じ物理コア2本 67us / 1本ずつ 66us）
- 事実: Session 共有は単体で効く。8並列で 41〜45us → 31〜32us (runs/s 約 +40%)。
  Session専用 ≒ 別プロセスなので、共有 Session 内の競合が原因と言える
- 事実: 共有をやめても 15us → 31us に伸びる。プロセスを分けても同じなので、
  プロセス内の共有物ではなく CPU 側の要因（同時実行に伴う性能低下）。内訳は未確認
- 事実: サーバー内の Run() (workers=8 で約 104us) は、同じ条件のネットワークなし (約 31us) の約3倍。
  ネットワーク処理が絡むときだけ出る分が最大の塊 (約 +70us)
  → 仮説（未検証）: ループバック TCP の割り込み/softirq が Run() の計測区間に入る、
    syscall でキャッシュが汚れる、など

### 訂正（自分の理解の修正）
- 「workers x intra_op のスレッドが奪い合う」は誤り。intra_op は Session 内の共有プールの大きさで、
  実測のスレッド数は「main + workers + (intra_op-1) + 1」。掛け算にならない
- 「EAGAINまで読み切るのは取りこぼさないため」は誤り。epoll は既定でレベルトリガなので、
  読み残しても再通知される。読み切る理由は syscall 削減。EPOLLET にするなら必須

### 設計メモ
- Session 専用は速いが重みが worker 数ぶんのコピーになる（mlp.onnx 25MB なら x8 で約200MB）。
  GPU では1 Session + バッチ化が自然なので、現状は共有を既定にしている

### 未解決
- サーバー内でだけ出る約 +70us の正体（perf や /proc/softirqs で確かめる余地あり）

Q1. workers=1、conns=16 で p50 が約3.6ms になるのはなぜか

worker 1本が16接続を1件ずつ順番に処理する。各クライアントは「送る→返事を待つ」を繰り返すので、
16件が同時に待っている状態になり、自分の番が来るまで前の15件の処理を待つ。
1件あたり約220〜240us（Run() 205us + 前処理/recv/send 約数十us）× 16 ≒ 3.6ms。
req/s=4,149 → 1件あたり約241us とも一致する。遅いのは推論が遅いからではなく「待ち行列」。
workers=8 にすると同時に8件を並行処理できるので p50 が 3,582→572us に下がった。

Q2. Run() が 205→275→403us と伸びるとき、コードの中で変わっているのは何か

run_inference のコード自体は何も変わらない。変わるのは「同じ Session の Run() を同時に呼ぶスレッド数」（1→8→20）。
M2 の切り分け結果と合わせると:
- 共有 Session 内の競合は一部（8並列で 41〜45us → 専用なら 31〜32us）
- Session を分けても 15us → 31us に伸びる = CPU 側の要因が主（同時実行で1本あたりが遅くなる）
- 今回は論理コア16に対し worker 20 + bench 16 以上のスレッドが走るので、Run() の壁時計時間に
  「CPU を取られて待った時間」も含まれる
内訳（メモリ帯域か、コア奪い合いか）は未確認。上の「仮説」参照。

Q3. workers=20、conns=16 のとき、実際に仕事をしているのは何本か

16本。acceptor はラウンドロビン（next）で接続を割り振るので、16接続は worker 0〜15 に1本ずつ渡る。
worker 16〜19 は接続を1つも持たず、epoll_wait で寝たまま（CPU を使わない）。
つまり workers が conns を超えた分は無駄になる。conns=100 なら20本とも5接続ずつ担当して全員働く。
（サーバーは条件ごとに起動し直しているので、next は毎回 0 から始まる）

Q4. Run() の計測区間に入っていない処理は何か

計測区間は run_inference 内の `session.Run(...)` の前後だけ（steady_clock の t0〜t1）。入っていないもの:
- 前処理（uint8→正規化 float のループ）、CreateTensor、後処理（argmax と memcpy）
- recv / send のシステムコール、epoll_wait から起きるまでの待ち、接続が順番待ちしている時間
- クライアント側の処理（bench のスレッド、send→recv の往復）
逆に入っているもの: Run() の最中にスレッドが CPU から外されて待った時間（壁時計で測っているため）。
だから「p50 − Run() 平均」が、ネットワーク・起床・待ち行列などの合計になる。

### 作ったもの
Phase 2 の C++ サーバー（acceptor + epoll ワーカー）の echo 部分を ONNX Runtime 推論に置き換えた「C++ Inference Server」。
- プロトコル: request = 784B / response = 44B（int32 予測 + float32×10）。固定長にして、接続ごとのバッファで溜めてフレーミング
- Session は1個を全ワーカーで共有（Run() はスレッドセーフ）。バッチ化は M4 で追加（ワーカー内の日和見バッチ）
- 測定ツール: infer_bench（レイテンシ分布 + 正解率 / dummy モード）、run_bench（ネットワークなしで Run() だけ）

### 作る → 測る → 問題を見つける → 改善する の流れ
| 段階 | 内容 | 数字 |
|---|---|---|
| 作る・測る (M1) | MNIST の MLP で推論サーバー | 約24〜42k req/s。ORT Run() は p50 の約5%（33us / 630us） |
| 問題を見つける (M2) | ワーカーを増やすと Run() が伸びる原因の切り分け | コア奪い合い・HT は否定。共有Session内の競合は一部。サーバー内でだけ約 +70us 出る分は未解決 |
| 推論が支配的な領域を作る (M3) | 重いモデル（5.8M param）で測定 | Run() 約205us、低負荷では p50 の約95%が推論。workers 1→8 で req/s 約6倍だが線形ではない |
| 改善する (M4) | dynamic batching | workers=8, conns=100 で 26,006 → 86,444 req/s（約3.3倍）、p50 3,342 → 1,034us、p99 8,833 → 2,595us |

### 説明できること（チェックポイント）
1. 軽い処理（MNIST）ではなぜ I/O が支配的か
   → Run() 33us に対し、ネットワークスタック・スレッド起床・クライアント側で p50 の約95%を使うから
2. 推論が重くなると何が変わるか
   → p50 のほぼ全部が推論になり、worker 数を増やすと効く。1本だと待ち行列がそのまま遅延になる（16接続 × 約220us ≒ 3.6ms）
3. worker を増やしても線形に伸びないのはなぜか
   → 同時に走る Run() が増えると1本あたりが遅くなる（205→275→403us）。共有Session内の競合は一部で、主因は CPU 側（内訳は未確認）
4. dynamic batching はなぜ効くか
   → 1件あたりの Run() が 200〜270us → 40〜60us に下がる（仮説: 重み23MBの読み出しを複数件で使い回せる）。バッチ1回は長くなるが、待ち行列が短くなり p50 は下がった
5. 待ち時間を足さずにバッチを作る仕組み
   → 読む → ready に並べる → まとめて Run()。推論中に溜まった分が次のバッチになる。低負荷ではバッチ1のままで遅延は増えない。バッチの上限は「担当接続数」
6. バッチ化しても結果が壊れていないことの確認
   → 添字 i で入力行・出力行・返信先 fd をそろえる。照合テスト 960件で不一致 0

### 学んだこと
- 「動いた」だけでは足りず、Run() 単体とクライアントから見た p50 を分けて測ったから、I/O 支配か推論支配かが分かった
- 変えたのはコードでなく「同時に呼ぶスレッド数」「1回に渡す件数」。性能は並列度とバッチサイズという運用パラメータで決まる
- 指標の設計（served 数、1リクエストあたりの Run()、平均バッチ）が、数字の解釈を助けた

### 未解決・限界
- サーバー内でだけ出る約 +70us の正体（perf / softirq で未確認）
- Run() が並列度で伸びる内訳（メモリ帯域かコア奪い合いか）
- workers=20, conns=100 の尻尾悪化（max=663ms）。taskset 分離で未検証
- 各条件1回の測定、bench とサーバーは同一マシン、乱数重みのため精度の話はしていない

### 次へ（Phase 7: TensorRT / GPU 最適化）
- GPU 版では 1 Session + バッチ化が自然な形（Session 専用はVRAMを食う）
- 今回のバッチ化の考え方（まとめて1回の推論）は GPU でさらに効くはず。転送コストの回収は Phase 4 M3/M4 の演算強度と同じ話


## 2026/10/27　M5（Request Queue）===============================================

### やったこと
- I/O 担当（epoll worker）と推論担当を分け、間に共有 Request Queue（mutex + condition_variable）を置いた。`infer_threads >= 1` で有効、0 なら従来のインライン
- 推論 worker は最大 `max_batch` 件を1回の Run() にまとめる。待ち時間は足さない（溜まっている分だけ取る）
- fd と Conn に触るのは持ち主の I/O worker だけ。返信は `{fd, gen, resp}` として持ち主の `done` キューに預け、eventfd で起こす。
  持ち主が `gen`（接続ごとの通し番号）を照合し、閉じた接続・同じ fd 番号の別の接続宛てなら捨てる
- 1接続につき未完了1件まで。2件目が揃ったら接続を閉じる（違反カウント）。Run() の例外は catch して接続を閉じる
- 推論の中心 `forward_batch()` をインライン版とキュー版で共通にした（比較を公平にするため）
- 再現性: CMake の `ORT_DIR` を `-D` で上書き可能に（既定は従来どおり）、`tools/export_mlp.py`、このREADMEに手順

### 正しさの確認
- MNIST で正解率 94.0% のまま（インライン／キュー batch=1／キュー batch=8）。対応のずれがあれば約10%に落ちる
- 荒い接続: 返信を待たず切る約7,900接続 → `stale_dropped=8004`（宛先の接続が閉じた返信を捨てた）、サーバー生存
- 未完了2件目を送る約6,300接続 → `violations=6272`、サーバー生存。試験後の通常ベンチも正常
- 注: 50接続・3秒の bench は正解率が約92.7%に出る。接続ごとに画像の開始位置が違い、10,000枚の一部しか使わないため（インライン版でも同じ。破損ではない）

- バッチなし(batch=1)では、キューは不利: 重いモデル100接続で 4,538 → 3,260 req/s (-28%)、p50 20.2 → 29.6ms。

- バッチありの高負荷（重い・100接続・batch=8）: スループットはほぼ同等（-9%、3回の幅と重なる）、
  p99 は 14.0 → 10.9ms (-22%)、max も短い。p50 は 5.8 → 6.7ms (+16%) と悪化
- 低負荷の重いモデル（16接続）はキューが有利: 4,335 → 6,018 req/s (+39%)、p50 3.56 → 2.51ms (-30%)。
  インラインは1 worker に約2接続しか無くバッチが作れない(平均1.0)のに対し、キューは全接続をまとめて平均2.8件
- 軽いモデル(mnist)はキューが不利: 16接続で req/s -20%、p50 +25%。100接続・batch=8 で req/s -7〜-11%、p50 +24〜30%。

- 事前の予想（Phase 2 M7 の教訓）どおり: 軽い処理では受け渡し（mutex・cv・eventfd）のコストが仕事より重い
- 重いモデルの p50 の内訳（100接続・batch=8・キュー）: p50 約6.4〜7.2ms ≒ キュー待ち 2.4〜2.9ms + Run() 約3.1ms（383us × 8件）+ 残り約1ms（I/O・受け渡し）
- 推論スレッド数が効く: I/O 4 + 推論 4 では 10,988 req/s（I/O 2 + 推論 6 の 14,212 より低い）。重いモデルは推論側がボトルネック

### 仮説（未検証）
- 低負荷の重いモデルでキューが +39% になる理由: バッチ化（平均2.8件）と、同時に走る Run() の数が減ること
  （インライン8並列 vs 推論6並列）の合算と思われるが、切り分けていない
- 高負荷で p99 が良くなる理由: I/O worker が推論で塞がらず、接続の受け付け・返信が遅れにくいため（未確認）

### 注意（測定の限界）
- 条件の多くは1回。重要な比較（100接続・batch=8）は3回だが、3回でもばらつきは大きい（インライン p99 12.6〜15.5ms など）
- この PC の絶対値は別 PC の M3/M4（例: 重いモデル・インライン・w=8・batch=1 が 約26k req/s）と大きく違う（この PC では 4.5k）。
  PC と ORT の版（1.30.0 と 1.31.0）が違うため、絶対値は比較しない。比べられるのは同じ PC 内の相対値だけ
- bench とサーバーは同一マシン。重みは乱数（精度は見ない）。スレッド総数は同じだが「計算に使える本数」は同じではない

### 説明できること（チェックポイント）
1. キューを入れると何が良くなり、何が悪くなるか → 良: 全接続でバッチを作れる・I/O が推論で塞がらない（尻尾が改善）。悪: 受け渡しのコスト・計算に使える本数が減る
2. 軽いモデルでキューが不利な理由 → 33us 級の Run() に対し、mutex・cv・eventfd の受け渡しが無視できない（Phase 2 M7 と同じ）
3. `gen` が必要な理由 → fd 番号は close 後に再利用される。推論中に接続が閉じて同じ番号の別の接続ができると、gen 無しでは他人に返信を送ってしまう（エラーにならず誤送信）
4. 推論 worker が自分で send しない理由 → 「gen を確認してから send」の間に持ち主が close すると割り込まれる（確認と送信が不可分でない）。close と send を同じスレッドがやれば割り込みが起きない
5. `touched` で eventfd への書き込みを worker ごとに1回にする理由 → 持ち主は起きたら done を空になるまで取り出すので1回で足りる。write はシステムコール

### つまずき
- 50接続・3秒のベンチで正解率が92.7%に出て、誤送信を疑った → 荒い試験をしないインライン版でも同じ値。bench の画像の選び方による見かけの差だった

  代わりに出力の誤差が 1.2e-7 → 4.4e-4（約 3,000 倍）。精度の良し悪しは見ていない（乱数重み）
- 厳密な FP32 の TensorRT は、小さい batch で遅い: batch=1〜32 で 360〜393us（他の GPU 経路は 207〜342us）。
  同じ TensorRT でも、TF32 を外すと batch=1 で 217 → 393us。大きい batch (256) では 339k と、FP32 系の中で最速
- ORT 経由の TensorRT が、ネイティブより速かった（FP16 で batch=1: 175 vs 207us、batch=256: 375 vs 436us）。ただしこれは
  TensorRT の性質ではなく、この測定ハーネスの差の可能性が高い（下の仮説）。どちらも同じ種類のエンジンを使っている
- ORT CUDA の TF32 より、TensorRT FP16 の方がさらに速い。精度を落とす代わりに速くなる、という段階が FP32 → TF32 → FP16 と見える
- 見立ての訂正: ネイティブ TRT FP32 が batch=1 で遅いのは、ラッパーが毎回 set_input_shape 等を呼ぶせいだと疑ったが、
  呼び出しを batch が変わったときだけにしても 393us のまま。同じラッパーの FP16 は 207us なので、ラッパーの手間が原因ではない

### 仮説（未検証）
- TF32 を外した TRT FP32 が小 batch で遅い理由: 厳密な FP32 では、TensorRT が別の（小さい batch に不利な）カーネルを選んでいる
- ORT 経由がネイティブより速い理由: ネイティブ側の CPU↔GPU 転送（`torch` の通常メモリからのコピー）が、ORT の内部の転送より重い。
  `trtexec` や固定メモリで確かめれば切り分けられる
- ORT-TRT の VRAM が +470MiB と大きい理由: CUDA プロバイダのバッファも持つため（未確認）

### 注意（測定の限界）
- 各条件 2 秒・1 回のみ。2 回測った M1 では PyTorch の batch=1 が 232〜265us と揺れた（約 10〜15%）。数%の差は誤差
- Windows 側のアプリも同じ GPU を使うため、使用率・VRAM は背景の揺れを含む（待機時 4〜31%）
- Python 経由の測定。C++ サーバー経由の値ではない（M3 で測る）。モデルは乱数重みの MLP（精度は見ない）

### 説明できること（チェックポイント）
1. batch=1 では GPU の利点が小さい理由 → 計算より固定費（起動・転送・呼び出し）が支配的
2. TF32 / FP16 が速くなる理由と代償 → 行列積で桁数を減らす。速くなる代わりに誤差が増える（5e-8 → 5e-5 → 4e-4）
3. FP32 で比べるとき TF32 をそろえる理由 → 既定の違い（ORT: 有効、PyTorch: 無効）が速度差に混ざるため

## 2026/10/28　M4（INT8: FP32 / FP16 / INT8 を精度と速度で比べる）===============================

### やったこと
- 精度が測れる重いモデルを作った: `tools/train_mnist_mlp.py`（mlp_dyn と同じ 784→2048→2048→10 を MNIST で 3 エポック学習。
  テスト正解率 97.11%、学習は GPU で約 4 秒）。`mnist_mlp_big.onnx`（重み 23MB）
- `tools/int8_bench.py`: 同じ ONNX から TensorRT の FP32（TF32 なし）/ FP16 / INT8 のエンジンを作り、精度と速度を比べる。
  INT8 は後訓練量子化（学習し直さない）。キャリブレーションに学習データ 512 枚（256 枚 x 2 バッチ）、INT8 にできない層は FP16 に任せる
- 再現手順: `python tools/train_mnist_mlp.py <MNISTのraw> models/mnist_mlp_big.onnx` → `python tools/int8_bench.py models/mnist_mlp_big.onnx <MNISTのraw>`

### キャリブレーションとは
INT8 は整数 256 段階しか表せない。FP32 の値を INT8 に写す倍率（スケール）を層ごとに決める必要がある。重みの範囲はモデルから分かるが、
各層の出力（活性化）の範囲は入力次第なので、代表的な入力を実際に流して値の分布を調べる。最大値をそのまま範囲にすると外れ値のせいで
細かさを失うので、TensorRT は分布から「どこで切り捨てるか」（情報の損失が最小になる位置）を選ぶ。

|---|---|---|---|---|---|---|---|---|---|
| FP32 | 97.11% | 100% | 0 | 22.3 MiB | 151 MiB | 3.8〜4.9s | 408 / 2.3k, 421 / 2.2k | 399 / 77k, 425 / 69k | 676 / 365k, 693 / 347k |
| FP16 | 97.11% | 100% | 0.029 | 11.2 MiB | 128〜146 MiB | 5.9〜6.4s | 212 / 4.3k, 229 / 3.9k | 234 / 122k, 230 / 124k | 430 / 590k, 388 / 606k |
| INT8 | 97.09% | 99.93% | 0.49 | 5.7 MiB | 186〜190 MiB | 17.2〜17.7s | 188 / 4.8k, 199 / 4.3k | 223 / 122k, 210 / 130k | 327 / 710k, 305 / 724k |

### 分かったこと（事実）
- INT8 の精度の低下は、ほぼ無い: 正解率 97.11% → 97.09%（-0.02 ポイント = 10,000 枚中 2 枚）。FP32 と違う予測は 7 枚（99.93% 一致）。
  FP16 は 97.11% で、予測も 100% 同じ。事前の予想（低下は 0.2 ポイント未満）どおり
- logits の誤差は FP16 で 0.03、INT8 で 0.49。予測（argmax）は変わらなくても、スコアそのものはずれる。確信度（softmax）を使う用途では注意
- エンジンのサイズは 22.3 → 11.2 → 5.7 MiB（FP32 の 1/2、1/4）。INT8 の作成は約 17 秒（FP16 の約 3 倍）でキャリブレーションを含む
- 速度（batch 256）: FP32 347〜365k → FP16 590〜606k（+62〜74%）→ INT8 710〜724k（FP32 比 +95〜109%、FP16 比 +19〜20%）
- INT8 の効果は大バッチだけ: batch 32 では FP16 と同等（122k vs 122k、124k vs 130k）、batch 1 は p50 188〜199us と FP16 (212〜229us) より少し短い程度。
  FP32 → FP16 の効果（+62〜74%）より、FP16 → INT8（+20%）のほうが小さい。事前の予想どおり
- VRAM は INT8 が最も大きい（186〜190 MiB、他は 128〜152 MiB）。エンジンは小さいのに増える理由は未確認

### 仮説（未検証）
- INT8 が FP16 にあまり勝たない理由: この MLP は計算より重みの読み込みで時間が決まる（メモリが先に限界）。重みが小さくなる効果は
  FP16 で得られており、INT8 の追加の効果は計算が増える大バッチだけに出る
- INT8 の VRAM が大きい理由: INT8 + FP16 の両方のカーネルを持つ、キャリブレーションの置き場が残る、など（未確認）

### 注意（測定の限界）
- 各条件 2 秒、2 回のみ。数%の差（batch 32 の INT8 vs FP16 など）は誤差。Python 経由の測定で、C++ サーバー経由の値ではない
- 正解率は MNIST のテスト 10,000 枚。分類が易しいので、INT8 の影響が出にくい。難しいデータでは違う可能性がある
- キャリブレーションは 512 枚のみ。枚数や選び方を変えたときの影響は見ていない
- INT8 の C++ サーバーへの組み込みは、今回はしていない

### 説明できること（チェックポイント）
1. INT8 にキャリブレーションが必要な理由 → 整数 256 段階に FP32 を写す倍率を、各層の出力の実際の範囲から決めるため。範囲は入力次第
2. INT8 が小さい batch で効かない理由 → 計算より固定費（転送・起動）が支配的で、計算が速くなっても見えない
3. 精度を落とす手段（TF32 / FP16 / INT8）の使い分け → 速度の得と、誤差・用途（確信度を使うか）の兼ね合い

5. GPU のプロバイダの失敗で黙って CPU に落とさず起動を止める理由 → 測定・運用の誤りが見えなくなるため（Phase 5 の「CUDA のつもりが CPU」）。早く、はっきり失敗させる（fail fast）
6. INT8 にキャリブレーションが必要な理由 → 整数 256 段階に写す倍率を、各層の出力の実際の範囲から決めるため。範囲は入力次第
7. GPU が速いのに全体が約3倍止まりの理由、推論スレッドを増やすと悪化する理由 → 全体の時間は Run() 以外（キュー待ち・I/O・負荷側）を含む。キューを分けるとバッチが小さくなり、GPU の固定費を割れなくなる

### 学んだこと
- 測定の設計が結果を左右する: 同一プロセスの VRAM・背景の使用率・TF32 の既定の違い・非同期の測り方・低い SM クロック。どれも「数字は出るが意味が違う」罠だった
- ボトルネックは動く: GPU が速くなると、Run() ではなくキュー待ち・I/O・負荷側が支配的になる。仮説（I/O worker が上限）は測って外れた
- 精度を落とす手段（TF32 / FP16 / INT8）は、速度の効きが大バッチに偏る。軽い仕事や小バッチでは固定費に埋もれる

### 未解決・限界
- サーバー内での約1ms の「残り」（I/O・受け渡し・負荷側）の内訳。Phase 6 の「サーバー内でだけ出る +70us」と同種の可能性（perf などで未確認）
- ORT 経由の TensorRT がネイティブより速かった理由（転送の差の可能性、未確認）。INT8 の VRAM が大きい理由
- 負荷側（bench）が同一マシンで先に限界になり、GPU の使用率は 13〜40%。GPU を使い切る条件では測れていない
- INT8 は C++ サーバーに組み込んでいない。精度は MNIST のみ、重みが乱数のモデルでは精度を見ていない。測定は各条件1〜2回、1台の PC・1つの GPU

### 次へ（Phase 8: Docker GPU / Monitoring / AI Infrastructure）
- 今回測った GPU 使用率・VRAM・キュー待ち・バッチ数を、実行中のサーバーから常時見られるようにする（Monitoring）
- GPU 版サーバーを Docker で動かす（NVIDIA Container Toolkit）。今回の `run_gpu_env.sh` が手で設定した、ライブラリの場所の問題がそのまま出る

## 2026/10/28　M2（infer_server を Docker イメージにする）===============================================

### やったこと
- `Dockerfile`（2 段階ビルド）: ビルド用（ubuntu:24.04 + g++/cmake + ORT の GPU 版 C++ パッケージ）と、実行用（`nvidia/cuda:13.0.3-cudnn-runtime-ubuntu24.04`
  に ORT の .so と `infer_server` だけ）。GPU ドライバはイメージに入れず、Toolkit が起動時に注入する。モデルは入れずにマウント。一般ユーザー（uid 10001）で動く。
  ORT のパッケージは SHA-256 を照合してから使う（ホストで取得した `ort-cache/ort.tgz` があればそれを使い、無ければビルド中に取得）
- `.dockerignore`（ビルドコンテキストから models / build / tools などを外す）
- 実行例（TcpServer/ で）:
  `docker build -t infer-server:gpu .` → `docker run --rm --gpus all --network host -v "$PWD/models:/models:ro" infer-server:gpu /models/mlp_dyn.onnx 2 1 0 32 1 cuda`

### 動作確認
- イメージ: 展開後 5.65GB（圧縮で 2.26GB。大半は CUDA/cuDNN のベースイメージ）。起動まで 4 秒（ウォームアップ込み）
- 学習済み mnist.onnx で、コンテナ経由の正解率 94.0034%（ネイティブと同じ）。GPU 使用率は最大 68%（待機時の背景を含む）
- ログに `use_tf32=0` が出て、厳密な FP32 の設定がコンテナの中でも効いている。`docker stop` は 1.2 秒で終了し、終了時の統計が出た
  （リクエスト数 117,317 は bench の完了数と一致）。SIGTERM が PID 1 の infer_server に届き、ハンドラが動いた

### 測定: ネイティブ vs コンテナ（mnist、cuda、I/O 2 + 推論 2、b32、100 接続、5 秒、Release ビルド、各 2 回）
| 構成 | req/s | p50(us) | p99(us) | max(ms) |
|---|---|---|---|---|
| ネイティブ | 41,215 / 41,584 | 2,295 / 2,300 | 4,911 / 4,363 | 19 / 13 |
| コンテナ `-p 8080:8080` | **27,904 / 26,463** | 3,356 / 3,479 | 7,214 / 7,850 | **100 / 128** |
| コンテナ `--network host` | 40,812 / 41,737 | 2,342 / 2,292 | 4,625 / 4,462 | 31 / 24 |

### 分かったこと（事実）
- コンテナそのもの（名前空間・cgroup・ファイルシステム）のコストは、ほぼ無い: `--network host` はネイティブと同じ（40.8〜41.7k vs 41.2〜41.6k req/s）
- ポート公開（`-p`）の経路で、スループットが約 33% 下がり（41.4k → 27.2k）、p50 が約 46% 伸び（2.30 → 3.42ms）、max が 100ms 超に悪化した
- `-p` で公開すると、ホストの 8080 番を持っているのは `docker-proxy`（root のユーザー空間プロセス、IPv4 用と IPv6 用の 2 つ）で、
  コンテナの IP（172.17.0.2:8080）へ転送している。`--network host` や停止後は、`docker-proxy` が無い

### 仮説（未検証）
- 遅くなる原因は docker-proxy の中継（接続ごとに2本の TCP 接続、ユーザー空間でのデータのコピー）。存在は確認したが、
  「proxy を無効にして（daemon.json の userland-proxy=false）再測定して差が消えるか」は、まだ確かめていない
- 今回の bench は同じマシンの localhost から接続している。ホストの外から来る接続は、docker-proxy を通らず iptables の NAT で
  転送されるはずで、その場合の差は違う可能性がある（未確認）

### つまずき
- `docker build` の中の ORT のダウンロードが、2 回止まった（`curl: (56) Recv failure: Connection timed out`、
  `curl: (28) Operation too slow`）。ホストからの同じ取得は 2.5MB/s で安定していた。ビルド中は CUDA イメージ（約 2GB）の取得と同時だったが、
  原因は特定できていない。→ ホストで `curl -C -`（途中から再開）で取り、SHA-256 を照合して、Dockerfile の `COPY` で渡す方式にした
- 取得を `... && rm ...; true` と書いた箇所が、照合に失敗しても手順全体を成功扱いにする誤りだった（fail fast の逆）→ `; true` を外した
- `pkill -f "文字列"` が、その文字列を含む自分のシェルまで止めた → プロセス名を厳密に指定する（`pkill -x`）
- `docker build` の出力を `tail` に通すと、終わるまで進行が見えない → `--progress=plain` でログファイルに出す
- 安全確認が、`docker rm -f` を含むコマンドを止めた（前回の残りを消す念のための行で、不要だった）→ `--rm` つきで起動し、削除そのものを不要にした

### 注意（測定の限界）
- 各条件 2 回・5 秒。bench とサーバーは同一マシン。軽いモデル（mnist）での値で、重いモデルや TensorRT では測っていない
- イメージに TensorRT は含めていない（provider は cpu / cuda）。含めると数 GB 増える

### 説明できること（チェックポイント）
1. 2 段階ビルドにする理由 → ビルド用のコンパイラ等を、実行用のイメージに持ち込まない（小さく、攻撃面も小さい）
2. GPU ドライバをイメージに入れない理由 → ホストのドライバのバージョンと合わせる必要があり、Toolkit が起動時に注入するため
3. `-p` が遅くなり、`--network host` では遅くならない理由 → `-p` は docker-proxy を経由する（仮説。存在は確認済み）。`--network host` はホストのネットワークをそのまま使う


## 2026/10/28　M3（メトリクスの出力口: /metrics）===============================================

### やったこと
- `src/metrics.h`（新規、外部ライブラリなし）: ヒストグラム（`Histogram<N>`、atomic の加算だけでロック不要）、Prometheus のテキスト形式の出力、
  小さな HTTP サーバー（`GET /metrics` と `GET /healthz` だけに答える、別スレッド、1接続ずつ順に処理）
- `infer_server.cpp`: 数える場所を足した（推論の経路には、atomic の加算と、有効時のヒストグラム観測だけ）。ポートは環境変数 `INFER_METRICS_PORT`（既定 9100、0 で無効）
- 出すメトリクス:
| 名前 | 種類 | 意味 |
|---|---|---|
| `infer_requests_total` | counter | モデルで処理し終えたリクエスト数 |
| `infer_batches_total` | counter | Run() を呼んだ回数 |
| `infer_run_seconds_total` | counter | Run() にかかった時間の合計 |
| `infer_queue_wait_seconds_total` | counter | キューで待った時間の合計（キュー版のみ） |
| `infer_errors_total{type=…}` | counter | protocol_violation / stale_response / run_failed / send_failed |
| `infer_queue_depth` | gauge | いまキューで待っている件数 |
| `infer_queue_depth_max` | gauge | 起動後の最大のキューの深さ |
| `infer_connections` | gauge | いまつながっている接続数 |
| `infer_connections_accepted_total` | counter | accept した接続の累計 |
| `infer_request_duration_seconds` | histogram | サーバー内の時間（784B が揃ってから返信を送り終えるまで） |
| `infer_batch_size` | histogram | 1回の Run() にまとめた件数 |
| `infer_build_info{provider,model,workers,infer_threads,max_batch}` | gauge | 設定（値は常に 1） |
- Grafana での使い方（M4）: 1秒あたり `rate(infer_requests_total[1m])`、p99 は `histogram_quantile(0.99, rate(infer_request_duration_seconds_bucket[1m]))`、
  1件あたりの Run() は `rate(infer_run_seconds_total[1m]) / rate(infer_requests_total[1m])`

### 動作確認（mnist、cpu、I/O 2 + 推論 2、b32、100 接続）
- 形式: Content-Type `text/plain; version=0.0.4`、12 の TYPE、64 行
- 整合: bench の完了数 191,280 = `infer_requests_total` = ヒストグラムの `_count`。接続数は負荷後に 0、累計 100、エラーは全部 0。
  終了時の統計 `requests=547,745` は 3 回の bench の合計（191,280 + 133,036 + 223,429）と一致
- 変な入力: 存在しないパス 404、POST 405、不正なバイト列は 405 で落ちない、クエリ付き `/metrics?x=1` は 200。
  ヘッダを途中で止める遅いクライアントが居ると、取得は最大約 3 秒待たされる（打ち切りの設計）。推論は影響を受けない
- `INFER_METRICS_PORT=0` でポートが開かない（`metrics=off`）

### 測定
サーバーの中の時間と、クライアントから見た往復時間（同じ負荷、同じ瞬間）:
| | p50 | p99 |
|---|---|---|
| サーバー内（`infer_request_duration_seconds` から計算） | 648us | 2,483us |
| クライアントから見た往復（infer_bench） | 1,908us | 5,079us |
→ 差の約 1.26ms（p50）は、サーバーの外（カーネルのネットワーク、epoll からの起床、bench 側のスレッド）にある。
Phase 6・7 で「サーバー内の約 1ms の残り」と書いていた正体が、初めてサーバーの内と外に切り分けられた

メトリクスを数えるコスト（同じ条件、有効と無効を 3 回ずつ交互、req/s）:
| 有効 | 無効 |
|---|---|
| 56,810 / 57,001 / 56,818（平均 56,876） | 56,475 / 57,133 / 57,111（平均 56,906） |
差は -0.05% で、ばらつきの範囲。10 回/秒で `/metrics` を取得し続けても、推論の req/s に影響は見えなかった

### 分かったこと（事実）
- 数えるコストは、atomic の加算だけなので、ほぼ無料（-0.05%）。ロックを使わない設計が効いた
- ヒストグラムがあると、平均では分からない p50/p99 が、サーバーの外から後で計算できる
- クライアントの往復の約 2/3 は、サーバーの外にある（この条件では）

### 制限・注意
- 1スレッドで順に処理する。遅いクライアントで、取得が最大約 3 秒止まる（Prometheus の取得タイムアウトの既定は 10 秒）
- 認証なし。接続数・エラー数・モデル名が見えるので、外部に公開するポートでは注意（M4 の構成では、Docker のネットワークの中だけで使う）
- p99 は、バケットの間を線形補間した近似（バケットの上限は 0.1ms〜1s の13個）
- 「サーバー内の時間」は、784B が揃ってから返信を送り終えるまで。受信側のカーネル待ちは含まない
- GPU の使用率と VRAM は、サーバー自身は出さない（M4 で別の仕組み）

### 説明できること（チェックポイント）
1. counter / gauge / histogram の違いと使い分け → counter は増えるだけ（rate で1秒あたりに）、gauge は今の値、histogram は区間ごとの件数（p99 を後から計算できる）
2. 平均だけでなくヒストグラムを使う理由 → 平均は尻尾（p99）を隠す。p99 は平均から計算できない
3. 数える側にロックを使わない理由 → atomic の加算は1命令で済み、推論スレッドが待たされない。読む側は別スレッドで、少しずれた値を読んでもよい（メトリクスは近似でよい）

- 取得（pull）型なので、サーバーは Prometheus の存在を知らなくてよい。サーバーは「いまの値を出す口」を持つだけで、取得の間隔・保存・グラフは別のコンテナが担当する
- 1 つのエンドポイントの数字（カウンタ）が、外から別に測った値（bench の完了数）と、ぴったり一致した。メトリクスを信じてよい根拠になる
- スループット（26k req/s）は、Phase 8 M2 の「`-p` 経由は約 33% 遅い」と整合する（ネイティブ 39k × 0.67）。docker-proxy を通る経路を、監視の画面でも見ていることになる
- 約束違反 1 件につき `stale_response` も 1 件出る。1 件目の返信が、閉じた接続宛てで戻ってくるため（gen による照合が働いている）

### 制限・注意
- GPU 使用率は、取得した瞬間の値（平均ではない）。5 秒ごとの取得では、短いピークを取りこぼす（上の表で 44% と 41% の差）。キューの深さも同じ
- VRAM は、Windows 側のアプリも含む GPU 全体の値（サーバー単体の使用量ではない）。WSL2 の `nvidia-smi` はプロセスごとの使用量を出さない
- Grafana のパスワードは、初回起動時にデータベースに入る。`.env` を後から変えても反映されない（変えるなら、`docker compose down -v` で grafana-data を消して作り直すか、画面で変更する）
- 画面の見た目（パネルの配置や見やすさ）は、私は API でしか確認できていない。表示を見て調整が必要

### 説明できること（チェックポイント）
1. pull 型（Prometheus が取りに行く）の利点 → サーバーは取得の間隔や保存を知らなくてよい。取得できなければ Prometheus 側で `up` が 0 になり、サーバーの停止に気づける
2. `rate()` が必要な理由 → カウンタは増えるだけの累計。「1秒あたり」にして初めて req/s になる
3. `histogram_quantile` で p99 を出す仕組み → 区間ごとの件数（累積）から、99% が入る区間の中を線形補間する。近似なので、バケットの上限の取り方に依存する
4. メトリクスのポートを公開しない理由 → 認証が無く、接続数・エラー数・モデル名が見える。Docker のネットワークの内側だけで使い、必要なものだけを 127.0.0.1 に出す

### 分かったこと（事実）
- `docker stop` / `docker kill` は「手で止めた」と扱われ、`restart: unless-stopped` が働かない。私が最初に `docker kill` で「クラッシュ」を再現しようとして、
  復旧しない結果が出たのは、実験の方法の誤りだった。再起動ポリシーを試すには、Docker の API を通さずにプロセスを終了させる
- 速い再起動は、`up` では見えない。取得間隔（5 秒）より再起動が速いと、Prometheus は一度も `up=0` を見ない
- 改善: プロセスの開始時刻のメトリクス `infer_start_time_seconds` を足し、パネル「Server uptime」（`time() - max(infer_start_time_seconds)`）と
  「Restarts (last 1h)」（`sum(changes(infer_start_time_seconds[1h]))`）を足した。再起動を2回起こすと、再起動回数が 0 → 1 → 2 と増え、稼働時間が 0 付近に戻った
  （`up` は 1 のまま）。Grafana 経由でも同じ値が返った
- 監視を入れても、推論の性能は変わらない（測定2）。推論サーバーが約 1.8 コアを使うのに対し、監視は数%

### 制限・注意
- 再現した「予期しない終了」は、終了コード 0 の SIGTERM。本物のクラッシュ（SIGSEGV など、非ゼロの終了）や OOM では試していない（`unless-stopped` は終了コードによらず再起動するはず。未確認）
- 再起動が連続すると、Docker は待ち時間を段階的に延ばす（バックオフ）。今回の2回では見えていない
- 各条件 3 回・15 秒。画面の見た目（パネルの配置など）は、API でしか確認していない

### 説明できること（チェックポイント）
1. 手で止めたときと、勝手に落ちたときで、再起動の挙動が違う理由 → 再起動ポリシーは「予期しない終了」への対策。`docker stop/kill` は意図した停止なので、再起動しない
2. 取得間隔より速い再起動が `up` で見えない理由と、見えるようにする方法 → `up` は取得した瞬間の成否だけ。開始時刻のメトリクスを出して `changes()` で数える
3. 監視を入れるコストの見積もり方 → 資源（CPU・メモリ）の実測と、性能への影響（有無の比較）の両方で語る

## 2026/10/29　M1（自作ロードバランサ `lb`）===============================================

### やったこと
- `src/lb.cpp`（新規）: epoll の L4 TCP プロキシ。クライアントの接続を、健康なバックエンドのうち「接続数が最少」のものへ中継する。
  独自の 784B/44B のプロトコルは見ない（接続単位の振り分け。同じ接続の間は同じバックエンド）
  - 使い方: `lb <listen_port> <host:port:health_port>[,...] [threads=2] [metrics_port=9101]`。host は IP でも DNS 名でもよく、DNS 名は 2 秒ごとに引き直す
    （`docker compose --scale` や Kubernetes の Service のように数が増減する相手に追従する）
  - proxy スレッド x N: 各スレッドが自分の epoll と SO_REUSEPORT の listen ソケットを持つ（同じポートへの accept をカーネルが振り分ける）
  - ヘルスチェックのスレッド: 1 秒ごとに各バックエンドの `/healthz`（9100）を見る。2 回連続の失敗で外し、2 回連続の成功で戻す。新しく見つけたものは、通るまで使わない
  - 受動の検知: データ用の接続が失敗したら、その場で外して別のバックエンドを選び直す（最大 3 回）
  - 切り離したバックエンドへの接続は、LB が閉じる（固まった相手でも、クライアントが再接続できる）
  - メトリクス（`/metrics`、metrics.h を再利用）: `lb_backend_up`、`lb_backend_connections`、`lb_backend_connections_total`、`lb_backend_connect_failures_total`、`lb_no_backend_total`、`lb_bytes_total`
- `infer_server`: ポートを環境変数 `INFER_PORT` で変えられる（同じマシンで複数台を動かすため）。`infer_bench`: 接続先を `INFER_HOST` / `INFER_PORT` で変えられる

### 設計の要点（事故を避けるために）
- バックエンドへの接続は非同期（`connect` を待たない）: 同期の connect だと、相手が落ちているとき SYN の再送で長く止まり、他の全接続を巻き込む
- 1 つの接続を 2 つの fd で見るので、片方を閉じて解放した直後に、同じ `epoll_wait` の結果に残った、もう片方の通知が、解放済みのメモリを触る危険がある
  （Phase 6 の「erase 後の参照」と同じ種類）。→ 閉じたら `dead` の印と fd の後始末だけを行い、メモリの解放は、その回の処理がすべて終わってから行う
- 書ききれなかった分は接続ごとに溜め、`EPOLLOUT` で続きを書く（順序を守る）。溜まりすぎ（1MB）なら接続を閉じる

### 動作確認（CPU の推論サーバー 3 台 + lb、ローカル、mnist）
- 振り分け: 30 接続が 11 / 9 / 10 に分かれた（2 本の proxy スレッドが同時に選ぶので、完全には均等にならない）
- 中継の正しさ: 同じ画像 3,000 枚の 44B の返信が、LB 経由と直接でバイト単位で完全一致（3000/3000）。784B を 100 バイトずつ細切れに送っても一致（200/200）
- 接続の出入り 20,000 回（8 スレッド）: 成功 20,000、失敗 0。要求の途中で切る/返信を待たずに切るを 1,000 回しても落ちない。
  LB の fd は 8 のまま（漏れなし）、中継中の接続は全部 0 に戻った
- 切り替え（再接続するクライアント 8 本）:
| 事象 | 検知の経路 | 検知までの時間 | クライアントへの影響 |
|---|---|---|---|
| `kill -9`（死んだ） | 受動（データ用の接続の失敗） | 0.1 秒 | 失敗 3 件 / 成功 約 14 万件 |
| `SIGSTOP`（固まった） | 能動（ヘルスチェックが 2 回連続で失敗） | 2.3 秒 | 3 件。凍結していた約 1/3 の接続が約 2.3 秒止まり、req/s が 7.2k → 5.8k に一時低下 |
| 復旧 | ヘルスチェックが 2 回連続で成功 | 再起動の約 1.4 秒後 / 再開の約 1.8 秒後 | |

### 分かったこと（事実）
- 「死んだ」は受動の検知で速く（0.1 秒）、「固まった」はヘルスチェックに頼るので遅い（2.3 秒）。固まった相手では TCP の接続は生きたままなので、
  ヘルスチェックと、こちらから接続を閉じる処理が無いと、クライアントは止まったままになる
- 検知の時間は、ヘルスチェックの間隔（1 秒）と、判断に要る連続回数（2 回）と、1 回の打ち切り（500ms）で決まる。短くすると速くなるが、一瞬の揺れで外す誤検知が増える
- 受動の検知で外したことを、最初はログに出していなかった。観測できない動きがあったので、時刻と理由つきのログを足した
  （この修正の前に、記録のコードの誤りで「復旧が再起動より前」という物理的におかしい結果が出たのを、ログと突き合わせて切り分けた）
- 速度: LB 経由は、直接より遅い（30 接続で 16.6k vs 32.7k req/s、p50 1,720 vs 881us）。原因（中継のコストか、CPU の取り合いか）は、M2 で切り分ける

### 制限
- 接続単位（L4）の振り分け: 同じ接続は同じバックエンドに固定される。接続数が少ないと偏る。リクエスト単位の振り分けは未実装
- 片方向だけの切断（half-close）は扱わない（片方が閉じたら両方を閉じる）。TLS なし、IPv4 のみ
- ヘルスチェックは、このサーバーの `/healthz`（HTTP）専用。DNS の引き直しは 2 秒ごと

### 説明できること（チェックポイント）
1. L4 と L7 のロードバランサの違い → L4 は接続（TCP）を中継し、中身を見ない。L7 は中身（リクエスト）を見て、1 件ずつ振り分けられる
2. バックエンドへの接続を非同期にする理由 → 同期だと、落ちた相手への接続で全体が止まる
3. ヘルスチェックを「2 回連続」で判断する理由 → 一瞬の失敗で外す誤検知を避けるため（代わりに、検知が遅れる）
4. 受動と能動の検知を両方持つ理由 → 死んだ相手は、接続の失敗で速く分かる。固まった相手は、ヘルスチェックでしか分からない
5. メモリの解放を回の最後にする理由 → 同じ回の epoll_wait の結果に、解放済みの Conn の通知が残っていて、触ると未定義動作になる
